## Outcome

Use the prototype as an instrumented testbench for the faithful retail PC port.
Maintain one shared runtime where the evidence supports it, with explicit
prototype/retail bindings rather than two independently maintained engines.
The useful result is reproducible native scenarios and corrections that benefit
the retail build, not completion of every debug-menu screen.

The next goal deliverable is a practical CLI-driven validation workflow, an
actually exercised multi-room scenario matrix, and a significant common-runtime
correction with its own prototype AND retail native evidence. This is an
intermediate milestone toward the original PC baseline, not a full-game or
remaster certificate.

## Shared implementation, qualified inputs

## Working loop

1. Inspect the current Git/checkpoint, live process handles and unfinished
   validations. Finish or explicitly record them before another experiment.
2. Inventory the already-working command/script channels before adding another
   tool. Prefer a small CLI for qualified room/point entry, finite warp and
   no-death ON/OFF. Commands must exercise real original input or a separately
   qualified execution boundary, not guessed flags or forced ready states.
3. Define a scenario before running it: exact build/disc profile, command,
   starting conditions, room/point, duration, expected visible effect, restore
   action, and failure criteria. An accepted request is not an observed result.
4. Exercise several useful rooms and situations: loading/transition, camera and
   rendering, and combat under controlled survival conditions. Use bounded
   inputs, not autonomous level-completion loops.
5. Compare the prototype native run with a named prototype-emulator reference
   when available. Keep reference limitations explicit. Then reproduce the
   relevant case on retail; prototype behavior is not automatically retail truth.
6. Select one real, reproducible defect. Decide whether the cause is common
   runtime behavior, a version-specific binding or an actual game difference.
   Fix the diagnosed layer rather than duplicating a workaround per version.
7. Add invented-data tests where appropriate, then rerun before/after and
   restoration/non-regression controls on BOTH native profiles. Use unchanged
   original captures, matched viewpoints where achievable, exact revision/hash
   provenance and visible limitations.
8. Publish the substantial finding and its reproducible instructions. Keep the
   tested matrix, failures, unsupported cases and next falsifiable test current.

baseline. Genuine game Save/exit/Load, hardware input, audible audio,
representative behavior and human campaign testing retain their separate gates.

trade simulation correctness for higher FPS.

multiplayer are separate reversible enhancement experiments, not features
promised by this workflow. No whole-engine Rust rewrite is planned.
